# Phase 07 Plan 01

## Goal

### Problem
The repo already exposes a broad iOS tool surface, but the shipped iOS runtime remains an idb-backed partial path while Android is the stronger execution baseline, leaving parity gaps in UI semantics, selector fidelity, record/replay maturity, observability, performance depth, and support-grade proof.

### Expected Outcome
- [ ] The planning workspace contains a durable implementation plan that explains how to close the current iOS-vs-Android capability gap without widening the MCP surface prematurely.
- [ ] Future execution can proceed in staged workstreams: deeper iOS UI backend, selector/action fidelity, record/replay hardening, observability/performance strengthening, and acceptance-proof lanes.
- [ ] The plan keeps support-boundary honesty explicit so iOS is promoted from `partial` only when runtime behavior and evidence actually justify it.

### Non-goals
- Shipping iOS parity in this planning slice.
- Adding new top-level MCP tool families before the current iOS backend is deepened.
- Claiming WDA/XCUITest-grade parity based on simulator-only or partial evidence.

## Plan

### Strategy
Keep the current MCP contracts and tool registry largely stable, then deepen the iOS adapter below that surface. Treat Android as the functional baseline, preserve deterministic-first behavior, and sequence the work so iOS first gets a stronger execution backend, then better selector/action semantics, then stronger recording and observability, and only then stronger support claims and acceptance lanes.

### Task Breakdown
1. Define the iOS parity boundary precisely: what Android already proves today, what iOS currently marks as `partial`, and which gaps are backend depth versus validation depth.
2. Design the deeper iOS UI execution backend in `ui-runtime-ios.ts`, including whether to extend the current idb path or add a WDA/XCUITest-grade element interaction lane while keeping fallback semantics explicit.
3. Harden selector-driven actions by improving iOS hierarchy semantics, target resolution, scroll/re-resolve loops, post-action verification, and ambiguity handling in `ui-runtime.ts` and `ui-model.ts`.
4. Upgrade iOS record/replay so `recording-runtime-ios.ts` and `recording-mapper.ts` produce more stable selector-driven steps and less coordinate-only degradation, with simulator and real-device expectations separated honestly.
5. Strengthen iOS logs, crash signals, diagnostics, and performance capture in `device-runtime-ios.ts` and `performance-runtime.ts` so iOS evidence density approaches the Android baseline.
6. Add targeted tests, capability-model updates, and proof lanes so iOS support promotion is backed by reproducible artifacts instead of implementation-only confidence.
7. Sync support-boundary docs and capability reporting only after the runtime and evidence paths prove the new maturity level.

### Risks / Unknowns
- The current idb hierarchy and action surface may have a hard ceiling that makes true parity impossible without a deeper WDA/XCUITest-backed path.
- iOS simulator success can overstate real-device readiness if the plan does not require separate real-device proof.
- Selector fidelity may remain weaker on mixed SwiftUI/UIKit or hybrid React Native / Flutter surfaces unless the hierarchy model is enriched rather than only retried more aggressively.
- Performance parity is not only a runtime issue; iOS proof can stay weaker if xctrace outputs remain thinner or more template-limited than Android Perfetto outputs.

### Done Criteria
- [ ] A future implementation session can use this plan to execute iOS parity work in bounded, reviewable slices instead of treating “make iOS like Android” as one opaque task.
- [ ] The plan identifies the exact runtime, model, recording, performance, test, and capability-reporting files that future work will need to touch.
- [ ] The parity roadmap preserves support-boundary honesty by separating backend maturity, evidence maturity, and support-claim promotion.

## Implement

### Planned Changes
- `.planning/phases/07-ios-parity-hardening/07-01-PLAN.md` — future-facing execution plan for staged iOS parity work.
- `packages/adapter-maestro/src/ui-runtime-ios.ts` — deepen iOS tree/action backend beyond the current bounded idb baseline.
- `packages/adapter-maestro/src/ui-runtime.ts` — share stronger iOS polling, snapshot normalization, and action execution loops.
- `packages/adapter-maestro/src/ui-model.ts` — improve iOS selector semantics, ambiguity handling, and post-scroll re-resolution support.
- `packages/adapter-maestro/src/device-runtime-ios.ts` — strengthen iOS logs, crash, diagnostics, screenshot, and lifecycle evidence behavior.
- `packages/adapter-maestro/src/recording-runtime-ios.ts` — improve iOS capture coverage, device handling, and context snapshots.
- `packages/adapter-maestro/src/recording-mapper.ts` — reduce low-confidence selector mapping and coordinate-only replay degradation on iOS.
- `packages/adapter-maestro/src/performance-runtime.ts` — deepen iOS performance capture and structured summary output.
- `packages/adapter-maestro/src/capability-model.ts` — promote support levels only when runtime behavior and proof change.
- `packages/adapter-maestro/test/*.test.ts` and `packages/mcp-server/test/*.test.ts` — add parity-oriented regression coverage and support-boundary assertions.

### Key Decisions To Preserve
- Do not add more MCP tools first; the main gap is iOS runtime depth under an already broad tool surface.
- Treat Android as the implementation and evidence baseline, not merely as a marketing comparison point.
- Keep deterministic-first behavior primary; if iOS requires fallback or lower-confidence behavior, the result envelope must continue to say so explicitly.
- Separate simulator-grade success from real-device support-grade success.
- Promote iOS support levels only after runtime, tests, and proof lanes all move together.
