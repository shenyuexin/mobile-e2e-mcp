# Phase 11 Plan 01

## Goal

### Problem
`executeCrashSignalsCapture` runs `adb shell ls -1 /data/anr` but never pulls the actual trace content. AI knows "ANR files exist" but cannot read the stack trace.

### Expected Outcome
- [ ] `pullAndParseAnrTraces` is a private function in `device-runtime-android.ts` (NOT on shared hooks interface)
- [ ] Primary path uses `adb shell "cat <escaped> | head -N"` (via boundedRemoteFileRead from 11-04)
- [ ] `adb pull` is fallback when `cat` fails
- [ ] `ls -1t` used instead of `ls -1` (recency ordering)
- [ ] `CrashSignalExecutionResult` extended via `platformExtensions?: Record<string, unknown>` (backward-compatible)
- [ ] ANR parser extracts `processName`, `pid`, `signal` only (no over-structured thread states)
- [ ] Temp files cleaned up in `finally` block
- [ ] Per-file timeout of 10s enforced
- [ ] Existing tests pass; new test added with mocked ANR content

### Non-goals
- Structured thread state parsing (deferred to future phase)
- CPU usage extraction from ANR traces
- Modifying shared `DeviceRuntimePlatformHooks` interface

## Plan

### Strategy
Add a private `pullAndParseAnrTraces` function in `device-runtime-android.ts` that uses `boundedRemoteFileReadBatch` (from 11-04) to read actual ANR trace content. Upgrade `ls` to `ls -1t` for recency ordering. Add `platformExtensions` bag to `CrashSignalExecutionResult` to carry the structured data without breaking the shared contract.

### Task Breakdown
1. Add private `pullAndParseAnrTraces` function in `device-runtime-android.ts`:
   - Accepts `repoRoot, deviceId, fileNames[], maxFiles, maxLinesPerFile, timeoutMs`
   - Uses `boundedRemoteFileReadBatch` to read each file
   - Parses `processName` (from `Cmd line:`), `pid` (from `----- pid N -----`), `signal` (from `timed out` patterns)
   - Returns `AnrTraceResult[]`
2. Update `executeCrashSignalsCapture`:
   - Change `ls -1` to `ls -1t` (recency sort)
   - After ls succeeds, call `pullAndParseAnrTraces` with top N files
   - Build content string with ANR trace sections
   - Set `platformExtensions.anrTraces` in result
3. Add `AnrTraceResult` interface in `device-runtime-android.ts` (private to module)
4. Add `platformExtensions?: Record<string, unknown>` to `CrashSignalExecutionResult` in `device-runtime-platform.ts`
5. Update `getCrashSignalsWithRuntime` to expose `platformExtensions` in tool output
6. Add tests: mock `boundedRemoteFileReadBatch` responses, verify content structure

### Risks / Unknowns
- `adb shell cat /data/anr/` may fail on some production devices — `adb pull` fallback handles this
- ANR filenames may contain shell-special characters — `shellEscape` in boundedRemoteFileRead handles this
- Temp file cleanup must happen in `finally` regardless of parser success/failure

### Done Criteria
- [ ] ANR trace content appears in `get_crash_signals` response `content` field as structured sections
- [ ] `platformExtensions.anrTraces` contains structured metadata per file
- [ ] Per-file timeout of 10s enforced
- [ ] Files > 2MB (via pull fallback) produce `{pullStatus: "too_large"}` without blocking other files
- [ ] Temp files cleaned up in all error paths
- [ ] `pnpm typecheck` passes
- [ ] Existing tests pass
- [ ] New test added with mocked ANR trace content
