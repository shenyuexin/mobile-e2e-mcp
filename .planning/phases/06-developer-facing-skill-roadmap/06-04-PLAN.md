# Phase 06 Plan 04

## Goal

### Problem
The planning workspace now has a shared baseline and an Android refinement slice, but iOS-specific readiness still needs its own downstream refinement so SwiftUI, UIKit, and mixed app surfaces inherit the shared contract without inventing a separate vocabulary.

### Expected Outcome
- [ ] The planning workspace contains a concrete `ios-e2e-readiness` draft that explicitly extends the shared baseline rather than redefining it.
- [ ] iOS-specific readiness checks are grouped into clear overlays for SwiftUI, UIKit, and mixed surfaces.

### Non-goals
- Publishing a real iOS skill file outside `.planning/`.
- Reworking the shared baseline vocabulary.
- Revisiting Android-specific guidance in this slice.

## Plan

### Strategy
Use the shared baseline as the contract layer, then add only iOS-specific checks where iOS runtime and UI semantics diverge: accessibility identifiers, launch/reset behavior, interruption handling, SwiftUI/UIKit surface differences, and transition stability.

### Task Breakdown
1. Define the iOS-specific extension boundaries on top of the shared baseline.
2. Draft a dedicated iOS skill spec artifact for SwiftUI, UIKit, and mixed surfaces.
3. Sync roadmap and state so Phase 06 can close once iOS refinement is complete.
4. Record verification and follow-on notes for future pressure testing and real skill publication.

### Risks / Unknowns
- SwiftUI examples can easily dominate and underweight UIKit or mixed apps.
- iOS launch/reset and interruption behavior may still need more pressure-testing before a real skill is published.
- Closing Phase 06 requires keeping Phase 05 visibly pending so planning completion does not look like product completion.
