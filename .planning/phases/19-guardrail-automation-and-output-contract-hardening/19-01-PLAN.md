# Phase 19 Plan 01

## Objective

- **What:** Add automated enforcement for the repository's architecture guardrails and introduce a second validation layer for tool-specific output payloads.
- **Why:** The repo already has strong written rules and a solid shared `ToolResult` envelope, but current enforcement still leans too heavily on reviewer discipline and tool-specific `data` payloads are not validated with the same rigor as the outer envelope.
- **Output:** Repo-owned validation scripts, CI wiring, descriptor/schema metadata for high-value tools, contract-focused tests, and a staged enforcement model that future work can extend without rediscovering the rationale.

## Goal

### Problem

Two repo-level weaknesses remain after the current capability/productization work:

1. **Architecture guardrails are strong in prose but weakly mechanized.** The repo documents clear rules for hotspot files, thin facades, dependency direction, and capability-governed PR hygiene, yet the main enforcement path is still review discipline plus PR templates.
2. **The shared tool envelope is stricter than the per-tool payloads.** `ToolResult` is a stable AI-facing shell, but many tool-specific `data` payloads can drift because the schema layer remains generic and runtime validation is not consistently attached to the tool registry.

### Expected Outcome

- [ ] Architecture guardrail violations can be detected by repo-owned validation commands before review or merge.
- [ ] High-value tool outputs have explicit tool-level payload validation in addition to the shared `ToolResult` envelope.
- [ ] README tool catalog truth can be checked against the live MCP registry with an auditable validation path.
- [ ] The rollout path distinguishes warning-mode adoption from blocking enforcement so the repo can tighten rules without destabilizing active work.

### Non-goals

- Broad runtime feature expansion unrelated to validation and enforcement.
- Replacing the shared `ToolResult` envelope with a brand-new result model.
- Full strict-schema coverage for every tool in the first slice.
- Large refactors of adapter-maestro hotspot files outside changes required to support guardrail checks.

## Plan

### Strategy

Execute the phase in two primary workstreams plus one sync lane:

1. **Workstream A — Guardrail automation:** Convert the most important written architecture rules into repo-local validation checks that run in CI and can also be invoked locally.
2. **Workstream B — Tool output contract hardening:** Layer tool-specific output payload schemas/validators onto the existing shared envelope, starting with the tools that most directly drive AI decisions.
3. **Workstream C — Truth-sync and rollout discipline:** Add registry/doc consistency checks, warning-to-blocking rollout rules, and documentation updates so future work can continue the pattern without hidden context.

The design goal is not maximal strictness on day one. It is **high-signal enforcement with a controlled rollout path**.

### Task Breakdown

1. **Inventory and prioritize guardrails that deserve mechanical enforcement.**
   - Map current written rules into check categories:
     - hotspot size and growth reporting
     - adapter-maestro thin-facade boundaries
     - reverse import / dependency-direction breaks
     - capability-governed PR note completeness
     - MCP registry ↔ public tool catalog drift
   - Separate rules into:
     - warning-first checks
     - hard-fail checks
     - deferred checks requiring AST-aware logic

2. **Introduce a repo-owned architecture guardrail validator.**
   - Add `scripts/validate-architecture-guardrails.ts` (recommended path).
   - First slice should support:
     - hotspot file line-count reporting
     - forbidden pattern detection in `packages/adapter-maestro/src/index.ts`
     - obvious platform-branch leakage in wrong modules
     - optional PR-body completeness check for guarded-path changes
   - Output must identify:
     - violated rule
     - file path
     - severity (`warn` vs `fail`)
     - suggested next action

3. **Wire guardrail validation into local and CI execution.**
   - Add a package script (recommended: `validate:architecture-guardrails`).
   - Decide where it runs:
     - as a dedicated CI step, or
     - folded into an existing validation lane
   - Keep first rollout warning-biased where false positives are likely.

4. **Define tool-output validation architecture without breaking the shared envelope.**
   - Keep `ToolResult<TData>` as the universal shell.
   - Add a second layer for tool-specific payload contracts, preferably descriptor-addressable.
   - Recommended model:
     - registry metadata points to a tool-specific output schema/validator
     - validator runs on dry-run/smoke outputs first
     - failures name the exact missing/extra/invalid field

5. **Harden Tier 1 tool outputs first.**
   - Start with tools whose payload quality most affects AI reasoning:
     - `perform_action_with_evidence`
     - `get_action_outcome`
     - `explain_last_failure`
     - `rank_failure_candidates`
     - `describe_capabilities`
     - `get_session_state`
   - For each, define expected payload shape and the minimum required fields for stable downstream consumption.

6. **Add contract-focused tests and validation fixtures.**
   - Add a focused test lane (recommended: `packages/mcp-server/test/tool-output-contracts.test.ts`).
   - Verify that representative tool invocations either:
     - satisfy their tool-specific schema, or
     - fail with a precise contract-validation result.
   - Extend `tests/README.md` only after the validation boundary is real.

7. **Add truth-sync validation for public tool catalog drift.**
   - Ensure README tool-catalog claims can be rechecked against the live registry.
   - The first version may live in the same architecture-guardrail validator if that keeps maintenance lower.
   - The validation should explicitly catch catalog-count and missing-tool drift.

8. **Stage enforcement and record the rollout policy.**
   - Warning mode first for noisy checks.
   - Promote only stable checks to blocking.
   - Document which checks are temporary warnings, which are merge blockers, and which remain future-work.

### Risks / Unknowns

- Regex-based guardrail checks may produce noisy results for large TypeScript files; AST-aware upgrades may be required later.
- Tool-specific schema hardening may expose existing payload drift that is currently tolerated by tests.
- Registry metadata may need light restructuring if the current `ToolDescriptor` shape is not a comfortable home for output validation hooks.
- If CI enforcement is made blocking too early, unrelated feature work could stall on guardrail false positives.
- README/tool-catalog sync can be done by validation first, but full auto-generation may need a separate follow-up slice.

### Key Decisions To Preserve

- Keep `ToolResult` as the common shell; do not fracture the entire tool-result model to fix tool-specific payload drift.
- Prefer **warning-first rollout** for noisy new enforcement checks, then tighten once false positives are characterized.
- Use repo-owned validation scripts rather than relying only on PR prose or reviewer memory.
- Treat tool-catalog sync as part of truth enforcement, not as a one-off doc cleanup.
- Start with **Tier 1 AI-critical tools** before expanding validation to the full catalog.
- Any future strictness increase should come with clear failure messaging and a bounded migration path.

### Follow-on Optimization Backlog (defer unless needed for the first slice)

1. Upgrade selected guardrail checks from regex/string heuristics to AST-aware validation.
2. Add automatic generation or snapshotting of the public tool catalog from the live MCP registry.
3. Expand payload validation from Tier 1 to Tier 2/Tier 3 tools.
4. Add schema-to-TypeScript consistency checks so runtime validators and TS contracts drift less easily.
5. Introduce an explicit exception registry for intentional hotspot-rule deviations, with expiry/owner fields.
6. Move tool input/output contract metadata closer to the descriptor layer to reduce duplicate registration.
7. Add a dedicated CI summary artifact for guardrail and contract-validation results so failures are easier to review.
8. Consider a future lint-style local preflight command that developers can run before opening a PR.
