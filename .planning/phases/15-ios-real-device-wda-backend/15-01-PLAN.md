# Phase 15 Plan 01

## Objective

- **What:** Replace Maestro YAML generation/execution for iOS real-device UI actions with direct WDA (WebDriverAgent) HTTP API calls.
- **Why:** Maestro requires installing helper apps (`dev.mobile.maestro` + `dev.mobile.maestro.test`) on every real device, with signing complications. WDA is the industry-standard underlying engine that Appium and all major tools use — we bypass the Maestro middle layer and talk directly to WDA's HTTP API.
- **Output:** New `WdaRealDeviceBackend` implementing `IosExecutionBackend`, using HTTP requests to the WDA server running on the device.

## Architecture Design

### Why WDA over Alternatives

| Option | Hierarchy? | Tap/Type? | Needs Signing? | Single Binary? | Maturity |
|---|---|---|---|---|---|
| **WDA direct** (this plan) | ✅ GET /source | ✅ POST /wda/tap, /wda/keys | Yes (one-time) | No (needs Xcode build) | ⭐⭐⭐⭐⭐ |
| Appium + XCUITest | ✅ | ✅ | Yes | ❌ (heavy) | ⭐⭐⭐⭐⭐ |
| pymobiledevice3 | ✅ | ✅ | No | ✅ | ⭐⭐⭐ |
| Maestro (current) | ✅ | ✅ | Yes (helper app) | ❌ | ⭐⭐⭐⭐ |
| devicectl | ❌ | ❌ | Yes | ✅ | ⭐⭐ (lifecycle only) |

**Decision:** WDA direct HTTP API. It's what Appium uses under the hood, so we get industrial-strength reliability without the Appium overhead.

### WDA HTTP API Mapping

| UiRuntimePlatformHooks | WDA HTTP Endpoint | Method |
|---|---|---|
| `buildHierarchyCaptureCommand` | `GET /source` | Returns accessibility tree as JSON |
| `buildTapCommand` | `POST /wda/tap` | `{x, y}` |
| `buildTypeTextCommand` | `POST /wda/keys` | `{value: [chars]}` |
| `buildSwipeCommand` | `POST /wda/dragfromtoforduration` | `{fromX, fromY, toX, toY, duration}` |
| `buildScreenshotCommand` | `GET /screenshot` | Returns base64 PNG |
| `probeAvailability` | `GET /status` | Returns WDA session info |

### Key Design Decision: HTTP Backend vs Command Builder Interface

**Problem:** `IosExecutionBackend` returns `string[]` (CLI commands for `executeRunner`). WDA uses HTTP, not CLI.

**Rejected approach: curl commands as command array** — this is a hack that breaks the command-builder semantic, makes error handling opaque, and adds shell escaping complexity.

**Accepted approach: WDA backend executes HTTP directly.**

The `WdaRealDeviceBackend` class will have two layers:
1. **Command builders** (matching `IosExecutionBackend` interface) — return structured HTTP request descriptors
2. **Execution methods** (new, internal) — use Node.js `fetch` to send HTTP requests to WDA

The execution layer (`ui-action-tools.ts`) will detect WDA backend type and call `backend.executeHttp()` directly instead of `executeRunner(backend.buildTapCommand(...))`.

```typescript
// In WdaRealDeviceBackend:
async executeTap(deviceId: string, x: number, y: number): Promise<WdaExecutionResult> {
  const url = this.getWdaUrl(deviceId);
  const response = await fetch(`${url}/wda/tap`, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ x, y }),
  });
  // ... parse response, return result
}
```

### WDA /source Output Format — Oracle Review Findings

**Verified:** WDA `GET /source` returns **JSON** (not XML). Appium actually converts JSON→XML on the server side.

**Field mapping required** (WDA JSON → parseIosInspectNodes expectations):

| WDA Field | parseIosInspectNodes expects | Mapping |
|---|---|---|
| `type: "XCUIElementTypeButton"` | `type: "Button"` | Strip `XCUIElementType` prefix |
| `name: "Maps"` | `AXLabel: "Maps"` or `label` | Map `name` → `AXLabel` |
| `rect: {x, y, width, height}` | `frame: {x, y, width, height}` | Rename `rect` → `frame` |
| `isEnabled: true` | `enabled: true` | Rename `isEnabled` → `enabled` |
| `isVisible: true` | (no direct field) | Map to `visible` (parser ignores unknown fields safely) |
| `children: [...]` | `children: [...]` | ✅ Direct match, recursive |
| (none) | `custom_actions` | ❌ Not present. Use type-based clickable detection: if type after stripping prefix is in `["Button", "Link", "Cell", "Switch", "Slider"]`, set `custom_actions: ["default"]` |
| `value: "Some text"` | `AXValue` or `title` | Map `value` → `AXValue` |
| `label: "Some label"` | `title` | Map `label` → `title` |

**Parser strategy:** Create a `parseWdaSource()` function that:
1. Fetches JSON from WDA `/source`
2. Transforms each node: strip prefix, rename fields, synthesize `custom_actions`
3. Calls existing `flattenIosInspectNodes()` on the transformed tree
4. Returns `InspectUiNode[]` — fully compatible with `parseIosInspectNodes()` output

    ```typescript
    export class WdaRealDeviceBackend implements IosExecutionBackend {
      readonly backendId = "wda" as const;
      readonly backendName = "WebDriverAgent";

      // For iproxy port forwarding (per-device)
      private getBaseUrl(deviceId: string): string {
        return `http://localhost:8100`; // iproxy forwards to device
      }

      // Direct HTTP execution methods (preferred path)
      async executeTap(deviceId: string, x: number, y: number): Promise<WdaExecutionResult> {
        const url = `${this.getBaseUrl(deviceId)}/wda/tap`;
        return this.postJson(url, { x, y });
      }

      async executeTypeText(deviceId: string, text: string): Promise<WdaExecutionResult> {
        const url = `${this.getBaseUrl(deviceId)}/wda/keys`;
        return this.postJson(url, { value: text.split("") });
      }

      async executeSwipe(deviceId: string, fromX: number, fromY: number, toX: number, toY: number, duration: number): Promise<WdaExecutionResult> {
        const url = `${this.getBaseUrl(deviceId)}/wda/dragfromtoforduration`;
        return this.postJson(url, { fromX, fromY, toX, toY, duration: duration / 1000 });
      }

      async executeHierarchyCapture(deviceId: string): Promise<WdaExecutionResult> {
        const url = `${this.getBaseUrl(deviceId)}/source`;
        const result = await this.getJson(url);
        // Transform WDA JSON → parseIosInspectNodes compatible format
        const transformed = this.transformWdaSource(result.value);
        return { success: true, data: JSON.stringify(transformed) };
      }

      async executeScreenshot(deviceId: string): Promise<WdaExecutionResult> {
        const url = `${this.getBaseUrl(deviceId)}/screenshot`;
        const result = await this.getJson(url);
        // result.value is base64 PNG
        return { success: true, data: result.value };
      }

      // Command builders (kept for interface compatibility)
      buildTapCommand(deviceId: string, x: number, y: number): string[] {
        return ["__wda_http__", deviceId, "POST", "/wda/tap", JSON.stringify({x, y})];
      }
      // ... other build*Command methods
    }
    ```

## WDA Setup Requirements (User-Facing)

Users need to complete these one-time setup steps before WDA backend works:

1. **Install libusbmuxd** (for iproxy): `brew install libusbmuxd`
2. **Clone WDA**: `git clone https://github.com/appium/WebDriverAgent`
3. **Open in Xcode**: `open WebDriverAgent/WebDriverAgent.xcodeproj`
4. **Configure signing**: Select team (free or $99 developer account), set bundle ID prefix
5. **Build to device**: Select device as destination, Product → Build For → Testing
6. **Start port forwarding**: `iproxy 8100 8100 --udid <deviceId> &`
7. **Verify**: `curl http://localhost:8100/status` → should return JSON with `sessionId`

The doctor command will check steps 1 and 7, and provide guidance for the rest.
