# Phase 06 Plan 01

## Goal

### Problem
`mobile-e2e-mcp` already has a strong harness foundation, but it does not yet have a durable internal roadmap for developer-facing skills that help app teams improve testability, readiness, debugging, and remediation. Recent exploration surfaced an unresolved naming and scope question: whether future skills should anchor on framework-specific names such as `compose-e2e-readiness` / `swiftui-e2e-readiness`, or broader platform-level names such as `android-e2e-readiness` / `ios-e2e-readiness` that can also cover non-Compose and non-SwiftUI app surfaces.

### Expected Outcome
- [ ] The planning workspace defines a clear roadmap spine, naming strategy, and scope boundary for developer-facing skills.
- [ ] The first backlog separates cross-platform baseline guidance from Android/iOS platform lanes, React Native/Flutter overlays, and failure-to-remediation helpers.

### Non-goals
- Implementing the skills themselves in this plan.
- Adding new MCP tool contracts or changing public support claims in this slice.
- Locking final prompt wording for every future skill before the roadmap exists.

## Plan

### Strategy
Use a platform-first taxonomy that matches the harness's actual product boundary: help developers make apps more automatable, diagnosable, and recoverable for AI-driven mobile E2E. Anchor roadmap naming on Android and iOS at the platform level, keep a separate cross-platform baseline for shared readiness guidance, and treat Compose, SwiftUI, React Native, and Flutter as overlays or subordinate lanes when their semantics materially differ.

### Task Breakdown
1. Lock the product boundary and naming decision rules for developer-facing skills.
2. Define the readiness rubric and the skill family map: cross-platform baseline, platform lanes, framework overlays, and failure/remediation helpers.
3. Prioritize the first execution backlog, including whether the first detailed spec should be a baseline skill or a platform lane.
4. Capture open questions and future handoff notes so later sessions can refine prompt structure, outputs, and tool integration without recovering hidden chat context.

### Risks / Unknowns
- Platform-level anchors may still need framework-specific sub-skills for areas such as Compose or SwiftUI animation and transition semantics.
- If roadmap execution later turns planning decisions into product behavior or public guidance, formal truth owners outside `.planning/` will need synchronized updates.
- A cross-platform baseline skill could become too generic unless it stays focused on deterministic entry, selectors, readiness signals, reset semantics, and evidence hooks.

### Done Criteria
- [ ] `06-01-SUMMARY.md` records the roadmap decisions, open questions, and recommended next execution slice.
- [ ] Future sessions can determine whether to start with a cross-platform baseline skill or a platform-specific lane without recovering earlier chat context.

### Key Decisions To Preserve
- `android-e2e-readiness` and `ios-e2e-readiness` are the recommended primary anchors; `compose-e2e-readiness` and `swiftui-e2e-readiness` stay subordinate overlays unless a later spec proves they need top-level status.
- A cross-platform readiness baseline should exist separately from platform lanes so React Native and Flutter remain first-class citizens rather than afterthoughts.
- Developer-facing skills should focus on readiness, debugging, evidence interpretation, and remediation—not generic UI implementation, design generation, or app-copilot behavior.
- Failure-to-remediation guidance belongs in the roadmap because it converts harness evidence into app-side developer action.
