# Phase 07 Plan 03

## Goal

### Problem
Even with the current iOS UI path, selector-driven actions remain weaker than Android because hierarchy semantics, ambiguity resolution, scroll-and-reresolve behavior, and post-action confirmation are not yet strong enough to avoid low-confidence or coordinate-heavy degradation.

### Expected Outcome
- [ ] The plan defines the exact selector/action fidelity improvements needed for iOS query, resolve, wait, tap, type, and scroll flows.
- [ ] Future implementation work can strengthen iOS semantics in `ui-model.ts` and `ui-runtime.ts` without broadening scope into unrelated observability or recording tasks.
- [ ] The parity work has explicit acceptance expectations for ambiguity handling, postcondition checks, and reduced coordinate fallback.

### Non-goals
- Replacing the whole iOS backend design.
- Implementing record/replay improvements.
- Promoting support levels before fidelity regressions are covered.

## Plan

### Strategy
Treat selector/action fidelity as its own layer above the chosen iOS backend. Define how iOS nodes should be normalized, how matching should rank and explain ambiguity, how scroll should re-capture and re-resolve targets, and how action success should be judged based on postconditions instead of transport success alone.

### Task Breakdown
1. Define the current iOS selector weaknesses and where they surface in query/resolve/tap/type/scroll tools.
2. Specify node-normalization, ranking, and ambiguity-reporting improvements needed in `ui-model.ts`.
3. Specify polling, scroll-and-reresolve, and post-action verification improvements needed in `ui-runtime.ts` and `ui-runtime-ios.ts`.
4. Define the regression tests needed to prove fewer low-confidence or coordinate-only paths on iOS.
5. Set the bar for what fidelity improvements must be true before any iOS support-level promotion is considered.

### Risks / Unknowns
- Better selector fidelity may depend on richer backend hierarchy fields, not only smarter ranking logic.
- Mixed SwiftUI/UIKit and hybrid framework surfaces may need different heuristics that should not silently leak into Android logic.
- Post-action verification can create longer action loops if it is added without bounded retry and clear failure semantics.

### Done Criteria
- [ ] The selector/action work is decomposed into model logic, runtime orchestration, and regression coverage.
- [ ] The plan states how to measure reduced coordinate fallback and better postcondition confidence.
- [ ] Future sessions can implement fidelity work without re-scoping recording or observability at the same time.

- Reduced coordinate fallback is a quality metric, not just a code cleanup preference.
- Selector semantics should become stronger without hiding ambiguity from the result envelope.
