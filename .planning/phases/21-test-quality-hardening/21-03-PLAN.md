# Phase 21 Plan 03 — Systemic Test Infrastructure and Output Contracts

## Objective

- **What:** Add coverage tooling, test the 5 previously untested MCP tools, replace the minimal custom JSON Schema validator with ajv, and consolidate repetitive stdio-server tests.
- **Why:** These are systemic improvements that raise the baseline quality of the entire test suite, not just individual files. Without coverage tooling, future drift cannot be measured. Without real tool tests, the untested tool surface remains a blind spot.
- **Output:** Coverage infrastructure, 5 new tool tests, upgraded contract validation, consolidated stdio test helpers.

## Part A: Coverage Tooling

### Add c8 (native ESM coverage for pnpm monorepo)

**Context:** Each package runs tests via `pnpm build && tsx --test test/*.test.ts`. c8 must wrap the `tsx --test` commands at the package level.

1. Add `c8` as dev dependency in root package.json
2. Add per-package `test:coverage` scripts (example for core):
   ```
   "test:coverage": "pnpm build && c8 --reporter=text --reporter=html --all --src src tsx --test test/*.test.ts"
   ```
3. Add root `test:coverage` script that runs all package coverage sequentially:
   ```
   "test:coverage": "pnpm --filter @mobile-e2e-mcp/core test:coverage && pnpm --filter @mobile-e2e-mcp/adapter-maestro test:coverage && pnpm --filter @mobile-e2e-mcp/adapter-vision test:coverage && pnpm --filter @shenyuexin/mobile-e2e-mcp test:coverage"
   ```
4. Add `.c8rc.json` config at root (for shared settings):
   - Exclude: `**/*.test.ts`, `**/node_modules/**`, `**/test/**`, `**/*.d.ts`, `**/dev-cli.ts`
   - Thresholds: **Do NOT set thresholds initially** — use c8 only for reporting, not gating. Add thresholds in a follow-up when baseline is known.
5. Run `pnpm test:coverage` to generate baseline report
6. Save coverage summary to `docs/testing/coverage-baseline.md`

### Rationale for c8 over nyc
- Project uses native ESM (`node:test`, `tsx`) — c8 uses V8 native coverage, no instrumentation needed
- nyc requires babel/swc transforms which would conflict with the tsx runtime
- Per-package coverage is necessary because each package has its own `tsx --test` invocation

### Why no thresholds initially
- Coverage thresholds are meaningless without a baseline. Setting arbitrary numbers (70/60) would either be too easy or block CI.
- First goal: generate a readable baseline report. Thresholds come after the team knows what "normal" looks like.

## Part B: Untested Tool Tests

### Add tests for 5 untested MCP tools
**Source:** `packages/mcp-server/src/server.ts` (tool handlers)

Create `packages/mcp-server/test/untested-tools.test.ts` with dryRun behavioral tests:

**IMPORTANT:** "Returns structure X" is NOT a sufficient assertion — that is type checking, which this phase is trying to eliminate. Each test must assert on:
- **Field presence AND non-emptiness** (e.g., `signals.length > 0`, `devices.length > 0`)
- **Semantic content** (e.g., DNS check returns actual host and resolved/not-resolved status, not just `{ dns: "..." }`)
- **At least one negative test per tool** (e.g., invalid session → error response, empty query → graceful handling)

1. `probe_network_readiness` — assert response includes `dns` and `http` sub-objects with `status` field (reachable/unreachable/unknown); negative test: invalid URL → error status, not throw
2. `compare_visual_baseline` — assert response includes `comparisonResult` with `match` boolean and `similarity` number; negative test: no baseline exists → graceful "no baseline" response
3. `capture_element_screenshot` — assert response includes element descriptor with `bounds` object (x, y, width, height) and `screenshotPath` string; negative test: element not found → error response
4. `take_screenshot` — assert response includes `path` (non-empty string), `timestamp` (valid ISO date), and `dimensions` (width/height > 0)
5. `list_devices` — assert response includes `devices` array; verify array contents match expected structure (deviceId, platform, status fields); negative test: no devices available → empty array, not error

**Approach:** Follow the existing `server.test.ts` dryRun pattern — invoke through `server.invoke()` with `dryRun: true`.

## Part C: Output Contract Hardening

### Replace custom JSON Schema validator with ajv
**Source:** `packages/mcp-server/test/tool-output-contracts.test.ts` (~280 lines)

Current issues with the custom validator:
- Only checks first 3 array items
- Doesn't enforce `additionalProperties: false`
- Doesn't test `oneOf`, `anyOf`, `pattern`, `format`
- Uses synthetic payloads, not real tool output

Proposed changes:
1. Add `ajv` as dev dependency
2. Replace `validateAgainstSchema` with `ajv.compile(schema)` + `ajv.validate(data)`
3. Add real tool output snapshots to `tests/fixtures/tool-output/` (one per tool schema)
4. Validate each real snapshot against its schema
5. Keep synthetic valid/invalid payload tests for edge cases
6. Add tests for: enum validation, numeric min/max, additionalProperties rejection

### Generate real tool output snapshots
1. Run each tool in dryRun mode through `server.invoke()`
2. Capture the `data` field of the response
3. Save as JSON fixtures in `tests/fixtures/tool-output/`
4. Add fixtures to version control

## Risks

- **ajv** is a new dependency — must be dev-only (`pnpm add -D -w ajv`), no runtime impact. Both `c8` and `ajv` are zero-runtime-impact dev dependencies — no production bundle change.
- Real tool output snapshots may change when tool behavior changes — fixtures must be updated alongside tool changes (document in PR template).
- c8 wrapping `tsx --test` in a pnpm monorepo may produce incomplete coverage if child processes aren't instrumented correctly — verify output before trusting baseline numbers.
- **Multi-platform coverage caveat:** c8 measures coverage from tests running on macOS. Android adapter code paths (adb shell commands, Android-specific parsing) and iOS-specific code paths (devicectl, xcrun) may have lower effective coverage when tested only on macOS. Note this in the baseline report and plan platform-specific test runs in CI.
- **Threshold recommendation for follow-up:** After baseline is established, set coverage thresholds at `baseline - 5%` to allow for minor drift while catching meaningful regressions. Example: if baseline is 72%, set threshold at 67%.
