# Phase 07 Plan 05

## Goal

### Problem
iOS already exposes diagnostics and performance tools, but the evidence path is thinner than Android’s stronger baseline, which reduces failure density, weakens remediation quality, and makes support-grade parity claims hard to justify.

### Expected Outcome
- [ ] The plan defines how iOS logs, crash signals, diagnostics bundles, screenshots, and performance capture should be strengthened.
- [ ] Future work can improve iOS evidence density without mixing support-claim updates into the same execution slice.
- [ ] The plan identifies where simulator behavior, real-device behavior, and xctrace template limits must remain explicit.

### Non-goals
- Replacing Android observability behavior.
- Treating performance capture as enough proof for full iOS parity.
- Changing user-facing docs in advance of stronger runtime evidence.

## Plan

### Strategy
Use Android’s richer evidence expectations as the benchmark, then strengthen iOS along the same dimensions: actionable logs, crash/diagnostics completeness, structured summary quality, and performance artifacts that are useful for failure attribution rather than just technically captured.

### Task Breakdown
1. Define the current iOS observability gaps relative to Android: logs, crash signals, diagnostics artifact completeness, and summary usefulness.
2. Specify the `device-runtime-ios.ts` and `device-runtime-platform.ts` changes needed for stronger evidence capture and clearer support levels.
3. Specify the `performance-runtime.ts` and `performance-model.ts` changes needed for more useful iOS performance summaries and artifact plans.
4. Define simulator-only versus real-device performance/diagnostics caveats and how they appear in result envelopes.
5. Define regression tests and validation commands that prove evidence quality improved instead of only plumbing more files through the adapter.

### Risks / Unknowns
- iOS toolchain/template limitations may cap feature equivalence even when evidence summaries improve.
- Adding more raw artifacts without stronger summarization can increase noise rather than diagnostic value.
- Some proof gaps may remain until separate real-device acceptance lanes exist.

### Done Criteria
- [ ] The observability/performance work is scoped as a distinct improvement slice with named ownership files.
- [ ] The plan preserves explicit support-level and environment caveats.
- [ ] Future sessions know how to validate evidence quality improvements, not just command execution.
