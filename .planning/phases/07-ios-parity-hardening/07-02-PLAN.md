# Phase 07 Plan 02

## Goal

### Problem
The current iOS UI runtime is explicitly idb-backed and partial, but the repo does not yet have a locked execution design for how iOS should graduate toward Android-grade selector-driven interaction without hiding weaker fallback semantics behind the same tool names.

### Expected Outcome
- [ ] A concrete backend design exists for the next iOS UI execution lane, including how hierarchy capture, element interaction, swipes, runtime probing, and failure semantics should work.
- [ ] The design states whether parity will come from extending the current idb path, introducing a deeper WDA/XCUITest-grade lane, or supporting both behind one deterministic-first routing layer.
- [ ] Future implementation work can modify `ui-runtime-ios.ts` and `ui-runtime.ts` without re-opening the architectural decision in every coding session.

### Non-goals
- Implementing the new backend in this slice.
- Promoting support-level claims.
- Reworking Android UI runtime behavior beyond what comparison needs.

## Plan

### Strategy
Treat this slice as a design-lock phase for the iOS UI backend. Compare the current Android and iOS runtime hooks, identify where idb semantics cap fidelity, define the desired adapter boundary for a stronger iOS lane, and record the deterministic path, fallback path, probe behavior, and support-level consequences before any implementation starts.

### Task Breakdown
1. Document the current iOS UI runtime path and its known ceilings: hierarchy source, tap/type/swipe primitives, probe behavior, and support-level notes.
2. Compare the Android UI runtime hook shape and identify which abstractions are already shared versus which iOS-specific gaps still leak upward.
3. Define the target iOS backend options and choose the preferred path for future implementation.
4. Record the exact adapter boundary changes needed in `ui-runtime-ios.ts`, `ui-runtime-platform.ts`, and `ui-runtime.ts`.
5. State the rollout guardrails: what remains `partial`, what can move first, and what proof is needed before capability promotion.

### Risks / Unknowns
- The current repo may need a new iOS backend dependency surface rather than a small refactor inside the existing idb path.
- A stronger iOS backend can increase environment complexity and doctor requirements if probe semantics are not redesigned together.
- Shared orchestration code in `ui-runtime.ts` can become muddier if the new iOS lane is added without a clean platform boundary.

### Done Criteria
- [ ] The backend path decision is explicit and durable enough for later implementation.
- [ ] Future work knows which files own runtime probing, command construction, and action execution semantics.
- [ ] The design keeps deterministic-first behavior and honest partial/fallback semantics intact.

### Key Decisions To Preserve
- Runtime maturity must improve below the MCP tool surface, not by adding more top-level tools.
- Probe/doctor behavior must evolve with the iOS backend so environment failures stay explicit and actionable.
- Any new iOS lane must preserve visible support-level semantics instead of making partial behavior look fully deterministic.
