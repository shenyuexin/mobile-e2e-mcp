# Phase 26 Plan 01 — Lock Page Context Outputs To `ToolResult<T>`

## Goal

### Problem

The source page-context design uses custom top-level statuses such as `blocked`, `interrupted`, and `clear`, plus standalone payload shapes like `{ status, reasonCode?, pageContext }`. That conflicts with the repo's existing `ToolResult<T>` envelope and would create immediate drift between contracts, MCP wrappers, and tool-output validation.

### Expected Outcome

- [ ] Phase 26 has an explicit repo-local decision for how page-context-related tools encode success, partial, blocked, and interrupted outcomes inside the existing `ToolResult<T>` envelope.
- [ ] The plan records where `pageContext`, policy/pre-flight details, interruption mapping details, and reason-code data belong in the response structure.
- [ ] Future Phase 26 slices can reference one canonical output model instead of re-deciding top-level status semantics per tool.

### Non-goals

- Implementing runtime page-context detection.
- Resolving `Platform` / `appId` / `targetAppId` modeling.
- Defining the final `PageContextType -> InterruptionType` mapper.
- Adding or removing any reason code before the output model is agreed.

## Scope

### In Scope

- Normalize page-context capability outputs to the current `ToolResult<T>` shape.
- Decide how page-context data should sit under `data` instead of a custom top-level schema.
- Define where blocked/interrupted/pre-flight outcomes should be represented.
- Record the minimum contract/code/doc truth owners that must stay aligned.

### Out of Scope

- Runtime detector internals.
- Policy rule implementation details beyond response-shape implications.
- Final support-boundary wording for shipped docs.

## Plan

### Strategy

Treat this slice as a contract-normalization gate. Before any runtime code starts, decide the canonical response envelope for page-context-facing operations by reading the live `ToolResult<T>` truth, identifying the exact fields already available for structured success/failure/partial outcomes, and recording a Phase 26-specific output model that future slices must reuse.

### Task Breakdown

1. Read the live `ToolResult<T>` contract and schema so the slice starts from current repo truth, not the external draft shape.
2. Inventory the page-context-related outcomes that need representation: normal success, blocked pre-flight, interruption-aware stop, partial/ambiguous result, and failure.
3. Define the canonical placement rules for `pageContext`, policy decision details, interruption mapping details, and reason-code usage inside the existing envelope.
4. Decide whether the page-context capability needs a dedicated `data.pageContextDecision`-style sub-object, or whether existing result-data conventions are sufficient.
5. Record the acceptance rule that no Phase 26 tool may introduce custom top-level statuses outside the repo-standard envelope.
6. Record the default type-placement/export rule for this slice: define new page-context contracts in a focused contracts module first, re-export them from `packages/contracts/src/index.ts`, then update downstream consumers after exports are in place.

### Risks / Unknowns

- Existing tools may already differ subtly in how they use `status`, `reasonCode`, and `data`, so the slice must distinguish repo baseline from local variation.
- A future reason-code choice such as `PAGE_CONTEXT_INTERRUPTED` may tempt implementers to redesign the envelope instead of fitting into it.
- Some blocked/interrupted semantics may be better represented as failure or partial outcomes, but this slice should document the decision rule rather than inventing runtime logic.

### Done Criteria

- [ ] The Phase 26 planning package contains an explicit output-model decision that stays within `ToolResult<T>`.
- [ ] Future slices no longer need to guess where page-context and pre-flight decision data belong in the response.
- [ ] The package explicitly forbids custom top-level status enums for Phase 26 tools.

### Key Decisions To Preserve

- Phase 26 must reuse the repo-standard `ToolResult<T>` envelope rather than introducing custom top-level status strings.
- Page-context-specific semantics belong under `data` and/or existing envelope fields, not in a parallel response contract.
- Reason-code expansion is a separate decision from envelope shape and must not be used as a reason to drift the result model.
- Any later Phase 26 tool or slice that proposes a new response shape must first justify why the existing envelope is insufficient.
- Default contract placement for new page-context types should be: focused contracts module first, `packages/contracts/src/index.ts` export second, downstream consumer updates third, then targeted build/typecheck verification.
