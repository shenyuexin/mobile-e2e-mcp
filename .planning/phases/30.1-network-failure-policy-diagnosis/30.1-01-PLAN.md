# Phase 30.1 Plan 01: Network Failure Policy Diagnosis

## Objective / Goal

Add an AI-first diagnosis capability that starts from an observed network failure and determines whether the failure is likely caused by release HTTP policy enforcement.

The phase should turn Phase 30's low-level `inspect_network_policy` checker into a higher-level failure attribution path:

```text
failed request -> http/release-like gate -> policy inspection -> structured failure reason
```

## Scope

- Add a first-class diagnostic entrypoint, tentatively `diagnose_network_failure`.
- Accept one explicit failed request and optionally JS network events captured by `capture_js_network_events`.
- Extract URL scheme, host, status, and transport error signals from failed request evidence.
- Gate release-policy attribution on:
  - valid URL
  - `http://` scheme
  - Android/iOS platform
  - release-like or artifact/config evidence
- Reuse `inspect_network_policy` for Android cleartext and iOS ATS policy decisions.
- Return structured, machine-consumable attribution and next-step guidance.
- Integrate with existing failure intelligence surfaces where appropriate:
  - `collect_debug_evidence`
  - `rank_failure_candidates`
  - `explain_last_failure`
- Document the recommended agent workflow.

## Out Of Scope

- Active proxying, packet capture, or request interception.
- Mutating app network policy, plist, manifest, or security config.
- Full arbitrary binary APK/IPA decoding beyond Phase 30's current support boundary.
- Guaranteeing backend health; backend reachability remains covered by `probe_network_readiness`.
- Replacing existing JS network event capture.

## Proposed Capability Contract

### Tool Name

`diagnose_network_failure`

### Input Shape

Add `DiagnoseNetworkFailureInput`:

- `sessionId?: string`
- `platform: Platform`
- `failedRequest?: NetworkFailureRequest`
- `events?: JsNetworkEvent[]`
- `artifactPath?: string`
- `androidManifestPath?: string`
- `androidNetworkSecurityConfigPath?: string`
- `iosInfoPlistPath?: string`
- `releaseHint?: "release" | "debug" | "unknown"`
- `dryRun?: boolean`

Add `NetworkFailureRequest`:

- `url?: string`
- `method?: string`
- `status?: number`
- `statusText?: string`
- `errorText?: string`
- `source?: "js_debug" | "log" | "manual" | "unknown"`

### Output Shape

Add `DiagnoseNetworkFailureData`:

- `platform`
- `analyzedRequest`
- `classification`
- `confidence`
- `policyInspection?`
- `releaseAssessment`
- `evidence`
- `nextSuggestions`

Add reason values:

- `likely_android_cleartext_blocked`
- `likely_ios_ats_blocked`
- `http_allowed_by_policy_failure_elsewhere`
- `https_not_cleartext_policy_related`
- `http_status_error`
- `backend_or_dns_unreachable`
- `policy_evidence_missing`
- `artifact_decode_unavailable`
- `invalid_or_missing_failed_request`

## Verification Approach

- Unit tests for pure diagnosis logic:
  - Android HTTP failure + blocked cleartext policy.
  - Android HTTP failure + allowlisted domain.
  - iOS HTTP failure + blocked ATS policy.
  - iOS HTTP failure + ATS exception domain.
  - HTTPS failure is classified as not cleartext-policy-related.
  - HTTP 4xx/5xx with policy allowed prefers status-error attribution.
  - Missing URL returns `invalid_or_missing_failed_request`.
  - Binary/unsupported artifact evidence returns `artifact_decode_unavailable`.
- MCP server tests:
  - tool is listed
  - invocation returns structured diagnosis
  - capability discovery includes the tool
- Existing integration tests:
  - stdio tool listing
  - typecheck/build

## Acceptance Criteria

- A user or agent can provide a failed network request and artifact/config evidence without manually inspecting plist/manifest files.
- The result clearly distinguishes:
  - release HTTP policy blocker
  - backend/status/network failure elsewhere
  - not applicable HTTPS failure
  - unknown due to missing/unsupported evidence
- The tool never treats missing policy evidence as allowed.
- Results include evidence references and next suggestions.
- Capability docs explain when to call each network tool.

## Success Criteria

- `diagnose_network_failure` is exposed as a first-class MCP tool.
- Android and iOS capability models report the new diagnostic capability.
- Tests prove the HTTP + release-policy attribution path on both platforms.
- Existing Phase 30 `inspect_network_policy` remains usable as the lower-level checker.
- README and agent guide describe the failure-first workflow.

## Risks / Decisions

- **Release-like detection is imperfect.** The initial implementation should prefer explicit `releaseHint` plus artifact/config evidence and report uncertainty rather than overclaim.
- **JS network capture is RN/Expo-specific.** The new tool should also accept explicit failed request payloads so native/Flutter users can use it.
- **Policy allowed does not mean request should succeed.** The diagnosis must preserve status/error/backend signals instead of returning a false negative.
- **Artifact decoding remains bounded.** Unsupported binary evidence should stay `unknown`, not allowed.
