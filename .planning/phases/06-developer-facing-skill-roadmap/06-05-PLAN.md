# Phase 06 Plan 05

## Goal

### Problem
Phase 06 now has planning-stage drafts for `mobile-e2e-readiness-baseline`, `android-e2e-readiness`, and `ios-e2e-readiness`, but those drafts have not yet been pressure-tested against real agent behavior. Without that validation, promoting them into real skill files would be premature.

### Expected Outcome
- [ ] The planning workspace contains a concrete pressure-test plan for all three readiness drafts.
- [ ] Future skill publication now has explicit pass/fail gates based on observed agent behavior, not only planning completeness.

### Non-goals
- Publishing real skill files under `~/.config` or `~/.opencode`.
- Changing public docs or support-boundary claims.
- Closing or overshadowing Phase 05 release-acceptance work.

## Plan

### Strategy
Use a TDD-for-skills framing: define baseline failure scenarios without the skill, pressure scenarios with the draft guidance, explicit loophole capture, and publication gates. Keep the slice inside `.planning` so skill quality is validated before any real distribution step.

### Read First
- `.planning/PROJECT.md`
- `.planning/ROADMAP.md`

- `.planning/phases/06-developer-facing-skill-roadmap/06-04-IOS-SKILL-SPEC.md`

### Task Breakdown
1. Define the RED/GREEN/REFACTOR pressure-test matrix for the three draft skills.
2. Create an observation template and loophole register so later executions capture failures consistently.
3. Define publication gates that must pass before any real skill files are created.
4. Sync roadmap/state so Phase 06 remains open for validation while Phase 05 remains clearly pending.

### Risks / Unknowns
- Pressure scenarios may show that the draft skill boundaries are still too broad or too vague.
- Some failures may come from prompt setup or execution noise rather than skill design, so observation discipline matters.
- Reopening a completed phase again increases planning complexity unless state updates stay explicit and minimal.

### Done Criteria
- [ ] `06-05-PRESSURE-TEST-MATRIX.md` defines RED/GREEN/REFACTOR scenarios and pass/fail rules.
- [ ] `06-05-OBSERVATION-TEMPLATE.md` and `06-05-LOOPHOLE-REGISTER.md` exist for repeatable execution.
