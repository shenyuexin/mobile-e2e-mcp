# Phase 26 Plan 02 — Lock Platform and App Identity Semantics

## Goal

### Problem

The external page-context design expands platform semantics to `android | ios-sim | ios-real` and alternates between `appId` and `targetAppId`. The live repo truth does not currently support that model: `Platform` is still `"android" | "ios"`, sessions persist `appId`, and MCP session-bound wrappers reject mismatched `platform` and `appId` before normalizing tool input. If Phase 26 drifts here, it will break contract consistency before detector code even starts.

### Expected Outcome

- [ ] Phase 26 records one contract-safe rule for how platform identity is represented without redefining the existing top-level `Platform` union.
- [ ] Phase 26 records one contract-safe rule for how `appId` is sourced and validated across start-session, session-bound tools, and any future page-context tool inputs.
- [ ] Future Phase 26 slices can treat iOS backend flavor or detection-lane detail as subordinate runtime metadata instead of a replacement for platform truth.

### Non-goals

- Implementing runtime detector behavior for Android, iOS simulator, or iOS real device.
- Finalizing the `PageContextType -> InterruptionType` mapper.
- Choosing a final reason-code path.
- Designing a new session model outside the repo's existing session-bound rules.

## Scope

### In Scope

- Lock the top-level platform truth for Phase 26 to the current repo contract unless a later contract change is explicitly justified.
- Decide how iOS backend flavor / execution-lane detail is represented without exploding `Platform`.
- Lock the app identity rule around `appId` versus any proposed alias such as `targetAppId`.
- Record how session-bound MCP wrappers constrain later Phase 26 tool design.

### Out of Scope

- Runtime lane selection internals.
- Adapter implementation details for WDA vs axe vs simulator command routing.
- Policy enforcement semantics except where platform/app identity rules interact with session-bound validation.

## Plan

### Strategy

Treat this slice as a contract-and-context gate. Start from the live repo truth: `Platform` is `android | ios`, `StartSessionInput` and many tool inputs use `appId`, and the MCP server currently rejects `platform`/`appId` mismatches against the active session before normalizing inputs. Use that truth to define a Phase 26-safe identity model in which backend flavor, lane, or detector source can exist as subordinate metadata without creating a parallel top-level platform contract.

### Task Breakdown

1. Read the live `Platform`, `Session`, and `StartSessionInput` contracts and record the current top-level identity model.
2. Read MCP session-bound input normalization/validation and record the existing rule: active session `platform`, `deviceId`, and `appId` are consistency-checked and normalized into tool input.
3. Decide how Phase 26 should represent iOS backend flavor or detection lane without replacing `Platform = "ios"`.
4. Decide whether `targetAppId` is unnecessary aliasing, a subordinate override concept, or a genuinely missing contract need — and record the decision rule explicitly.
5. Record the acceptance rule that no Phase 26 slice may introduce `ios-sim` / `ios-real` as top-level platform values unless the repo's formal contracts are deliberately changed first.

### Risks / Unknowns

- The external design may have used `ios-sim` / `ios-real` for clarity, but reifying that directly in contracts would drift from current repo truth.
- Some future detector APIs may want to distinguish backend flavor at input time; this slice must prevent that need from silently mutating the top-level platform model.
- If `targetAppId` is introduced casually, it may conflict with session-bound wrapper logic that already validates and normalizes `appId`.

### Done Criteria

- [ ] The Phase 26 planning package contains one explicit rule for top-level platform truth.
- [ ] The package contains one explicit rule for `appId` ownership and any allowed override behavior.
- [ ] Future slices no longer need to guess whether iOS execution flavor should be modeled as platform, runner profile, backend metadata, or tool-local data.
