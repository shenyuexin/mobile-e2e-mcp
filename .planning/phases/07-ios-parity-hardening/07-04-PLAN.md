# Phase 07 Plan 04

## Goal

### Problem
The repo has an iOS recording path, but it remains bounded and simulator-first, and replay fidelity can still degrade into weak selector mapping or coordinate-heavy output compared with the stronger Android baseline.

### Expected Outcome
- [ ] The plan defines how iOS recording capture, context snapshots, raw event parsing, selector recovery, and replay output should be strengthened.
- [ ] Future execution can improve iOS recording without mixing it into backend-path and observability work.
- [ ] The plan keeps simulator support and real-device support explicitly separated so recording maturity is described honestly.

### Non-goals
- Rewriting general replay orchestration.
- Claiming real-device parity without separate evidence.
- Broadening recording into an open-ended UX capture project.

## Plan

### Strategy
Use Android recording maturity as the reference, then identify where iOS capture channels, context snapshots, selector reconstruction, and rendered flow output still lose deterministic value. Focus on making recorded iOS events map back to selector-driven tools more reliably and on making residual low-confidence steps visible instead of silently optimistic.

### Task Breakdown
1. Define the current iOS recording limitations: simulator-first behavior, capture channels, context snapshots, and selector reconstruction gaps.
2. Specify the `recording-runtime-ios.ts` changes needed for stronger capture coverage and device handling.
3. Specify the `recording-mapper.ts` changes needed to improve selector recovery and confidence reporting.
4. Define replay-output expectations so generated flows prefer selector-driven steps and mark weak fallbacks clearly.
5. Define regression tests and validation scenarios for simulator and, separately, future real-device recording.

### Risks / Unknowns
- iOS raw event streams may have intrinsic ambiguity that prevents full selector reconstruction without richer snapshots.
- Real-device capture may require different permissions, tooling, or event sources than simulator capture.
- Replay quality can look improved in YAML while still being operationally weak if confidence semantics are not tested rigorously.

### Done Criteria
- [ ] The iOS recording/replay gap is decomposed into capture, mapping, replay quality, and validation tasks.
- [ ] The plan makes simulator-first versus real-device scope explicit.
- [ ] Future implementation has a named regression target for recording quality, not only code refactors.
