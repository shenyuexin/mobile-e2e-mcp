# Phase 10 Plan 01

## Goal

### Problem
Android real-device replay (`run_flow`) currently hard-depends on Maestro helper apps (`dev.mobile.maestro`, `dev.mobile.maestro.test`), which causes repeated install friction and blocks replay even when direct adb-based action paths are already available.

### Expected Outcome
- [ ] Android real-device replay has a self-owned primary execution lane without mandatory helper-app precheck.
- [ ] Replay failure output clearly distinguishes owned-lane failures vs optional Maestro fallback failures.
- [ ] Existing Android direct action/recording behavior remains backward compatible.

### Non-goals
- Replacing all Maestro integration in one phase.
- Rewriting iOS runtime in this Android-focused slice.
- Expanding replay grammar beyond the bounded MVP command set defined in this plan.

## Plan

### Strategy
Keep existing Android helper-app-free primitives (`adb input`, `uiautomator dump`, getevent capture) and introduce an Android owned replay lane for **physical-device live replay** only. Treat Maestro helper-app replay as explicit fallback instead of hard precondition.

### Scope Freeze (explicit)
- In-scope: Android physical-device `run_flow` live replay default backend selection and fallback semantics.
- In-scope: Planner/orchestrator mapping for bounded MVP command set in this plan.
- Out-of-scope: iOS runtime behavior changes, simulator replay semantics, and flow grammar expansion.
- Out-of-scope: broad contract redesign beyond fields/reason codes explicitly listed in Planned Changes.

### MVP Command Support Matrix (authoritative for this phase)
| Command category | Command | MVP status | Owned lane behavior | Maestro fallback behavior |
|---|---|---|---|---|
| app lifecycle | `launchApp` | ✅ supported | supported via owned Android runtime | optional fallback |
| app lifecycle | `stopApp` | ❌ unsupported | deterministic terminal fail (`UNSUPPORTED_OPERATION` + stopReason label) | optional fallback only before first mutating step |
| app lifecycle | `clearState` | ❌ unsupported | deterministic terminal fail (`UNSUPPORTED_OPERATION` + stopReason label) | optional fallback only before first mutating step |
| interaction | `tapOn` | ✅ supported | selector/point mapping via planner + orchestrator | optional fallback |
| interaction | `inputText` | ⚠️ conditional | only when deterministic focus/target evidence exists | fallback before first mutating step if policy allows |
| interaction | `scroll` | ❌ unsupported in MVP | deterministic terminal fail (`UNSUPPORTED_OPERATION` + stopReason label) | optional fallback only before first mutating step |
| interaction | `swipe` | ❌ unsupported in MVP | deterministic terminal fail (`UNSUPPORTED_OPERATION` + stopReason label) | optional fallback only before first mutating step |
| interaction | `back` / `home` / `killApp` | ❌ unsupported in MVP | deterministic terminal fail (`UNSUPPORTED_OPERATION` + stopReason label) | optional fallback only before first mutating step |
| assertion | `assertVisible` | ✅ supported (bounded) | supported as bounded replay check | optional fallback |
| assertion | `assertNotVisible` | ❌ unsupported in MVP | deterministic terminal fail (`UNSUPPORTED_OPERATION` + stopReason label) | optional fallback only before first mutating step |
| flow control | nested `runFlow` | ❌ unsupported in MVP | deterministic terminal fail (`UNSUPPORTED_OPERATION` + stopReason label) | optional fallback only before first mutating step |

Notes:
- This matrix intentionally tracks current repository parser/orchestrator maturity; unsupported items are explicit, not implicit.
- Assertion semantics that rely on Maestro-specific wait/retry behavior stay out of owned MVP unless explicitly implemented and verified.
- `policy-allowed only` in this phase means the existing `run_flow` descriptor/session policy already authorizes execution under the current `write` scope; this plan does not add backend-specific scopes, policy branches, or new policy descriptors.

### Backend Selection Matrix (must implement exactly)
| Platform / target | Flow mode | Primary backend | Fallback backend | Hard-fail condition |
|---|---|---|---|---|
| Android physical | live replay | `owned-adb` | `maestro` (policy-allowed only) | Neither backend allowed/available |
| Android simulator | live replay | existing path (unchanged in this plan) | none in-scope | existing behavior |
| iOS any | live replay | unchanged in this plan | unchanged | unchanged |
| Any | dry-run preview | existing step-orchestrated preview | none | unchanged |

Rules:
- Backend is selected once at replay start and emitted in replay evidence/timeline labels.
- Unsupported-command fallback eligibility is decided from full-flow plan scan before step 1 executes.
- Runtime-detected low-confidence text targeting may trigger fallback only if no mutating step has completed yet.
- For mutating flows, fallback is **whole-flow only** (not per-step) once execution begins.
- For non-mutating flows, per-step fallback is still disallowed in this phase to keep semantics simple and auditable.
- If first mutating step already executed in owned lane and a later unsupported step appears, return deterministic terminal fail instead of mid-flow backend swap.
- If fallback is selected but helper apps are missing, terminate with explicit reason (`DEVICE_UNAVAILABLE`) plus fallback-blocked labels; do not silently continue in mixed mode.
- For fallback gating in this phase, `launchApp`, `tapOn`, and `inputText` are mutating; `assertVisible` is non-mutating.
- In existing result fields, `owned-adb` maps to `executionMode: "step_orchestrated"` and `maestro` maps to `executionMode: "runner_compat"`.
- Backend/fallback evidence is emitted through existing surfaces (`summaryLine`, replay timeline `summary/detail`, `ReplayStepOutcome.stopReason`, `ReplayStepOutcome.actionabilityReview`) unless contracts are explicitly extended in the same PR.

### Backend Selection Persistence
- Backend is determined during `replay-step-planner.ts` full-flow pre-scan and emitted as `resolvedBackend: "owned-adb" | "maestro"`
  in the planner output envelope.
- `replay-step-orchestrator.ts` reads `resolvedBackend` from planner output and does not re-evaluate it per step.
- If fallback is triggered at runtime, the orchestrator updates `resolvedBackend` to `"maestro"` in the replay timeline metadata
  and sets `fallbackTriggeredAtStep: <stepNumber>` for auditability.
- Session context (`sessionId`-scoped artifact) stores final backend selection in replay summary for post-mortem triage.

### Appendix A: Fallback State Machine

```
                          ┌─────────────────────┐
                          │  Planner pre-scan   │
                          │  (full flow parse)  │
                          └─────────┬───────────┘
                                    │
                     ┌──────────────┼──────────────┐
                     ▼              ▼              ▼
              All steps        Has unsupported   Has unsupported
              supported?       step BEFORE        step AFTER first
                     │         first mutate?       mutate step?
                     ▼              ▼              ▼
              owned-adb         maestro          owned-adb →
              primary           primary          terminal fail
                                (policy-ok)      (UNSUPPORTED_OPERATION)
```

Decision table:

| Flow has unsupported step? | Position relative to first mutate? | Fallback allowed? | Final backend |
|---|---|---|---|
| No | N/A | N/A | `owned-adb` |
| Yes | Before first mutate | Yes (policy) | `maestro` |
| Yes | After first mutate | No | `owned-adb` → terminal fail |
| Yes | Before first mutate | No (policy blocks) | terminal fail (`DEVICE_UNAVAILABLE`) |

### Risks / Unknowns
- Some complex replay steps may still need Maestro fallback in MVP and must be clearly surfaced.
- OEM multi-user/device-policy environments may alter adb command behavior; need explicit evidence in verification.
- If backend selection drifts between runtime and scripts, operator experience will remain inconsistent.
- Highest-risk failure mode: silent semantic drift in text/focus-dependent steps (`inputText` sent to wrong target while replay appears successful).

### Text / Focus Safety Rules (non-negotiable)
- Owned backend must only execute `inputText` when all of the following are true in current replay step context:
  - resolved target is unique (no ambiguity) and derived from stable selector evidence (`resourceId` / `identifier` preferred; text-only only when unique),
  - immediately preceding focus-producing action in owned lane targeted the same resolved node,
  - most recent UI snapshot before text entry shows no conflicting focused editable element.
- If any condition fails before the first mutating step completes, fallback may be used when policy allows and helper apps are available.
- If any condition fails after a mutating step has completed, terminate replay deterministically; do not mid-flow swap backends.
- Never report `success` for text-entry step when target confidence is below deterministic threshold.

### Rollback Plan
- Keep Maestro replay path intact as existing `runner_compat` lane.
- Operational rollback for this phase: revert Android physical live replay default backend selection to existing `runner_compat` path in `flow-runtime.ts`, while retaining added diagnostics/evidence labels.
- This phase does **not** introduce a new public feature-flag name; any future public rollback switch must be introduced and documented in a separate plan.
