# Phase 07 Plan 06

## Goal

### Problem
Even if iOS backend, selector, recording, and evidence paths improve, the repo still needs an explicit promotion slice that decides when `partial` can change, what proof counts, and which formal truth owners must be updated together.

### Expected Outcome
- [ ] The plan defines the proof bar for promoting iOS support boundaries toward Android-grade claims.
- [ ] Future implementation knows which tests, validation lanes, and docs must move together before capability reporting changes.
- [ ] The support-promotion slice remains impossible to “complete” on code changes alone.

### Non-goals
- Implementing all prior parity work inside this plan.
- Using doc wording to get ahead of runtime or evidence truth.
- Treating simulator-only confidence as final support proof.

## Plan

### Strategy
Treat support promotion as its own acceptance phase. Define what runtime maturity, regression coverage, simulator proof, real-device proof, capability-model updates, and public-doc sync must all be true before any iOS tool group changes from `partial` to stronger support language.

### Task Breakdown
1. Define the minimum runtime and evidence prerequisites for iOS support promotion.
2. Define the required automated regression coverage and targeted acceptance lanes.
3. Define the minimum simulator proof and minimum real-device proof separately.
4. Define the exact support-boundary fields, capability-model notes, and docs that must be updated together.
5. Define the no-promotion conditions so partial behavior cannot be re-labeled early.

### Risks / Unknowns
- Real-device proof may remain operationally expensive, delaying support promotion even after runtime improvements land.
- Partial success in one iOS tool family can create pressure to over-promote unrelated tool groups.
- Docs and capability metadata can drift again if promotion rules are not explicit and test-backed.

### Done Criteria
- [ ] The repo has a future-proof support-promotion gate for iOS parity work.
- [ ] Capability promotion is tied to runtime truth, regression truth, and proof-lane truth together.
- [ ] Public wording can only move after the acceptance slice says it may.
