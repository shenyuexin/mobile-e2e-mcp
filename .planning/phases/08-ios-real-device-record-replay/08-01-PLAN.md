# Phase 08 Plan 01

## Goal

### Problem
Current iOS record/replay is simulator-first (`simctl` + idb snapshot association), while the capability model still blocks promotion until both simulator and real-device proof lanes exist.

### Expected Outcome
- [x] The repo gets an executable implementation path for iOS **physical-device** record/replay instead of simulator-only assumptions.
- [x] Proof-lane design is explicit: simulator and real-device evidence are independently runnable, comparable, and auditable.
- [x] Future promotion decisions can be made from deterministic acceptance evidence, not from partial runtime intuition.

### Non-goals
- Promoting iOS support claims in this plan alone.
- Reworking unrelated Android parity flows.
- Hiding physical-device uncertainty behind doc-only wording changes.

## Plan

### Strategy
Treat iOS physical-device record/replay as a dedicated capability lane: first close runtime-path feasibility and deterministic capture semantics, then land replay fidelity + evidence outputs, then wire a real-device acceptance lane that can gate support promotion alongside the existing simulator lane.

### Task Breakdown
1. **Runtime feasibility & contract mapping**
   - Define the physical-device capture primitives (event source, snapshot source, timestamp alignment) and explicit failure reason codes.
   - Decide what remains deterministic vs bounded fallback on real-device iOS.
2. **iOS physical-device recording runtime slice**
   - Extend `recording-runtime-ios.ts` / platform hooks to support physical-device target resolution and bounded capture start/stop lifecycle.
   - Preserve simulator path behavior and avoid regressions.
3. **Replay mapping + confidence slice**
   - Update `recording-mapper.ts` expectations so real-device recordings prefer selector-driven steps and annotate confidence/fallback consistently.
   - Add parity checks for degraded coordinate-only outputs.
4. **Acceptance lane & scripts slice**
   - Add/extend scripts and workflow inputs so iOS physical-device record/replay can run as a distinct acceptance lane.
   - Keep simulator and real-device artifacts partitioned in reports.
5. **Capability + docs sync gate slice**
   - Update `capability-model`, MCP descriptions, and docs only according to measured lane evidence.
   - Keep `partial` or proof gate where evidence is still missing.

### Risks / Unknowns
- iOS physical-device event capture sources may be lower fidelity than simulator logs, requiring stronger snapshot or app-context coupling.
- Physical-device lane reliability may depend on host/device tooling versions, increasing CI/self-hosted variability.
- Replay quality may appear improved while remaining brittle if confidence and ambiguity metadata are not enforced in tests.

### Done Criteria
- [x] A future implementation session can execute iOS physical-device record/replay in bounded slices with named owners and tests.
- [x] Acceptance lane requirements are explicit enough to fail loudly when real-device proof is absent.
- [x] Support-promotion decisions remain coupled to runtime behavior + lane evidence + docs sync.
