# Phase 30 Plan 01: inspect_network_policy MCP capability

## Goal

### Problem

Release builds can fail plain HTTP requests even when device connectivity and backend reachability are healthy, because iOS ATS and Android cleartext policy block unapproved HTTP domains. The current network tools probe runtime connectivity, but they do not inspect release policy configuration.

### Expected Outcome

- [x] A new `inspect_network_policy` MCP tool returns structured Android/iOS policy findings for provided HTTP URLs or domains.
- [x] Android checks cover `usesCleartextTraffic`, `network_security_config`, `cleartextTrafficPermitted`, and domain-specific allow rules when readable XML config is provided.
- [x] iOS checks cover `NSAppTransportSecurity`, `NSAllowsArbitraryLoads`, `NSExceptionDomains`, `NSExceptionAllowsInsecureHTTPLoads`, and `NSTemporaryExceptionAllowsInsecureHTTPLoads` when readable plist data is provided.
- [x] The result distinguishes `allowed`, `blocked`, `unknown`, and `not_applicable` so AI agents do not confuse missing evidence with policy failure.
- [x] Capability reporting and README tool lists include the new release policy inspection boundary.

### Non-goals

- Runtime traffic interception, proxy setup, latency/error injection, or response mocking.
- Backend health checks; `probe_network_readiness` remains the runtime connectivity tool.
- Automatic mutation of `AndroidManifest.xml`, `network_security_config.xml`, or `Info.plist`.
- Full binary Android manifest decoding without local Android tooling. If an APK cannot be decoded deterministically, return `unknown` with remediation guidance.

## Plan

### Strategy

Add an additive, read-only capability with deterministic parsing first. The implementation should work reliably with source/config files, read XML policy evidence directly from ZIP-based APK/IPA artifacts when available, and gracefully report conditional support when binary artifact decoding is unavailable. Keep policy analysis pure and unit-testable in `adapter-maestro`; wire MCP/tool contracts separately.

### Risks / Unknowns

- Android APK manifests are binary XML in normal builds; deterministic decoding may require `aapt`, `aapt2`, or `apkanalyzer`. MVP must not pretend unsupported extraction is a policy result.
- Info.plist may be binary; macOS `plutil` can decode it, but direct plist path tests should stay pure and deterministic.
- `NSAllowsArbitraryLoadsInWebContent` does not allow native networking; the tool should not over-report it as general HTTP allow.
- Matching Android subdomains and iOS exception-domain semantics must be explicit and conservative.

### Key Decisions To Preserve

- This is static release-policy inspection, not active network probing.
- Missing or undecodable config produces `unknown`, not `allowed`.
- HTTPS endpoints are `not_applicable` because ATS/cleartext allowlisting only concerns plain HTTP.
- iOS web-content-only ATS exceptions must not be treated as native networking permission.
- Android domain-specific network security config overrides are only reported when the referenced config XML is available.
