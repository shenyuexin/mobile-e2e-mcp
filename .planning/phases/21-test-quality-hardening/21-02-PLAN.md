# Phase 21 Plan 02 — Medium-Path Test Strengthening

## Objective

- **What:** Add error-path, edge-case, and missing-branch tests to 9 files currently scored MEDIUM.
- **Why:** These files have good happy-path coverage but systematically skip error paths, which are the most likely failure modes in production. Error handling is where real bugs hide.
- **Output:** 9 test files with meaningful error-path and edge-case coverage.

## Source Files and Gaps

### 1. device-lease-store.test.ts
**Source:** `packages/core/src/device-lease-store.ts`

**NOTE:** `assertSafeSegment` is internal (not exported). Test it indirectly through the exported functions that use it. **Pre-flight:** Verify that `assertSafeSegment` is already covered by existing tests (e.g., in a shared utils test file). If not, the path traversal tests below will be indirectly testing an untested function — acceptable for this phase, but file a follow-up to add direct `assertSafeSegment` tests.

Add tests for:
1. `loadLeaseByDevice` with corrupt JSON file (SyntaxError fallback returns undefined)
2. `loadLeaseByDevice` with non-existent device file
3. `listLeases` with mixed valid/invalid JSON files (invalid files silently skipped)
4. `listLeases` when leases directory does not exist (returns [])
5. `persistLease` with invalid deviceId containing path traversal characters (`../evil`) — should throw via `assertSafeSegment`

### 2. failure-memory-store.test.ts
**Source:** `packages/core/src/failure-memory-store.ts`

Add tests for:
1. Deduplication: write same actionId twice → verify replacement not append
2. 200-entry cap: write 210 entries → verify only 200 retained
3. Ordering: write entries out of order → verify newest-first ordering
4. Corrupt JSON in index file → SyntaxError returns fallback []

### 3. interruption-policy.test.ts
**Source:** `packages/core/src/policy-engine.ts` (~324 lines)

**SCOPE NOTE:** This file has 6+ testable surfaces. To keep this plan manageable, focus on the 3 most critical error/edge paths:
1. `loadAccessPolicyConfig` — valid YAML parsing, missing file fallback (structural: returns defaults, not undefined)
2. `requiredPolicyScopesForTool` — test representative tool-to-scope mappings (at least 3 tools, including one unknown tool)
3. `isToolAllowedByProfile` — allow-list match, deny-list match, default-allow

**DEFERRED to follow-up:** `loadAccessProfile` (profile loading), `evaluateNetworkRetryPolicy`, `resolveInterruptionPlan` (priority sorting). These are lower-risk and can be added after this phase lands.

### 4. session-scheduler.test.ts
**Source:** `packages/core/src/session-scheduler.ts`

**VERIFIED FINDING:** `packages/core/test/session-scheduler.test.ts` is a **3-line stub** (just imports + `test` import). There is NO unit test for `runExclusive` in the core package. The existing test at `packages/mcp-server/test/session-scheduler.test.ts` is an integration test through `start_session`/`end_session` — it does NOT test lock acquisition, timeout behavior, or error propagation directly.

**This plan adds the FIRST unit test for `runExclusive`.**

Add tests for:
1. `runExclusive` with task that throws → verify markIdle and lock.release still called (finally block behavior)
2. `runExclusive` with 3+ tasks → verify FIFO ordering
3. `runExclusive` success path → verify timeline event recorded with correct actionId/status

### 7. crash-attribution.test.ts
**Source:** `packages/adapter-maestro/src/crash-attribution.ts`

If this test proves difficult to construct (crash fixture format is complex), defer this item entirely.

### 8. recovery-tools.test.ts
**Source:** `packages/adapter-maestro/src/recovery-tools.ts`

**NOTE:** These are complex integration functions that call through the server. Tests should use the same `server.invoke()` + `persistActionRecord` pattern as the existing refusal-path tests.

**IMPORTANT:** These tools run in `dryRun` mode — they will always return a success-like response. Tests should assert on:
- **Request structure**: The tool receives and processes the expected parameters
- **Response shape**: The returned data has the expected fields (e.g., `replayedSteps`, `recoveryPath`, `success`)
- **NOT actual recovery behavior**: dryRun mode does not execute real recovery, so "recovery succeeds" cannot be meaningfully tested

Add tests for:
1. `replayLastStablePathWithMaestro` — set up a recorded session with stable steps → verify dryRun response includes `replayedSteps` array with expected count
2. `recoverToKnownStateWithMaestro` — set up session in a recoverable state → verify dryRun response includes `recoveryPath` field with step descriptions
3. `recoverToKnownStateWithMaestro` with partial recovery — verify response includes retry metadata if first attempt would have failed (mock via evidence content)

### 9. ocr.test.ts
**Source:** `packages/adapter-vision/src/` (and ocr provider)

**STEP 0 — Pre-flight export verification:** Before writing any tests, run `grep -n "export" packages/adapter-vision/src/**/*.ts` to confirm what functions are actually exported. The adapter-vision package uses `MacVisionOcrProvider` which calls macOS native Vision API. If `parseOcrResult` or equivalent parsing functions do NOT exist as separate exports, skip item 3 below and test only the exported `findTargetByQuery` function.

Add tests for:
1. `findTargetByQuery` with empty query string — verify graceful handling (return no matches or all matches, not throw)
2. `findTargetByQuery` with overlapping bounding boxes — verify consistent resolution when two targets share the same area
3. If `parseOcrResult` or equivalent parsing function exists: test with malformed/non-standard input structure. **If it does not exist as a separate export, defer this item.**

## Risks

- `interruption-policy.test.ts` YAML loading tests use inline YAML strings to avoid fixture management overhead. Keep YAML minimal — only the fields needed for the assertion.
- `session-scheduler.test.ts` core test file is currently a 3-line stub. This is the FIRST unit test for `runExclusive` — mock the filesystem lock carefully to avoid real file I/O.
- `session-lease.test.ts` stale lease tests are inherently file-based. Use deterministic lease file manipulation rather than actual process checks.
- `recovery-tools.test.ts` success-path tests require complex setup (recorded sessions with stable steps). Mirror the existing `persistActionRecord` pattern from refusal-path tests. Assertions target response shape, not actual recovery behavior.
- `ocr.test.ts` tests depend on macOS Vision API — Step 0 export verification must pass before proceeding. If exports are missing, defer.
- `crash-attribution.test.ts` already has 11 tests. The crashedThread test may be deferred if fixture construction is too complex.
- `governance.test.ts` already has 5 solid tests. Supplements are minimal edge cases only — low risk of regression.

## Test Quality Gate

Same as Plan 01: each new test must assert on **observable behavior**, not just function invocation or type checks. Error-path tests should verify that the function **fails correctly** (correct error type, correct message, correct fallback value), not just that it returns something truthy.
