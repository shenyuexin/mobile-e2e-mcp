# Phase 26 Plan 04 — Bridge `PageContextType` Into The Existing Interruption Taxonomy

## Goal

### Problem

The external page-context design introduces new surface-level categories, but the repo already has an interruption taxonomy (`system_alert`, `action_sheet`, `permission_prompt`, `app_modal`, `overlay`, `keyboard_blocking`, `unknown`), classifier logic, and policy-resolution flow. Without an explicit one-way bridge, Phase 26 would create two parallel classification systems: one for page context and one for interruption handling.

### Expected Outcome

- [ ] Phase 26 records one explicit rule that `PageContextType` describes **surface semantics**, while `InterruptionType` continues to describe **governance/action semantics**.
- [ ] Phase 26 records one explicit one-way mapping layer from `PageContextType` into `InterruptionType`.
- [ ] Future Phase 26 slices can reuse the existing interruption detector/classifier/resolver path instead of inventing a second policy-routing taxonomy.

### Non-goals

- Implementing the final `PageContextType` enum itself.
- Replacing or redesigning the repo's existing interruption taxonomy.
- Rewriting interruption policy resolution logic.
- Choosing the final reason-code strategy for page-context outputs.

## Scope

### In Scope

- Define the semantic boundary between page context and interruption handling.
- Define the one-way `PageContextType -> InterruptionType` bridge rule.
- Define what additional signals the mapper is allowed to consult beyond raw page-context type.
- Record the truth owners that must stay aligned when the mapper is implemented later.

### Out of Scope

- Full runtime implementation of page-context detection.
- Full redesign of interruption policy rules.
- Detailed cache invalidation or fallback behavior not directly related to mapping semantics.

## Plan

### Strategy

Treat this slice as a taxonomy-bridge gate. Start from live repo truth: interruption tools already exist as thin MCP wrappers over adapter logic; `InterruptionType` is already formalized in contracts; the detector/classifier use signals such as owner package/bundle, container role, visible text, and blocking signals; and the resolver already routes policy decisions based on `classification.type`. Use that truth to define a Phase 26-safe rule: page context may introduce richer surface semantics, but only an explicit mapper may translate those semantics into the existing interruption model used by policy, telemetry, and recovery.

### Task Breakdown

1. Read the live `InterruptionType`, `InterruptionClassification`, and policy-rule contracts so the slice starts from current repo taxonomy rather than the external draft's terminology.
2. Read the current detector/classifier/resolver path and record which interruption signals already drive type selection and policy routing.
3. Define the Phase 26 semantic rule: `PageContextType` is about what surface is visible; `InterruptionType` is about how the harness should reason about and handle that surface.
4. Define the one-way mapper rule, including which extra signals the mapper may consult (for example owner bundle/package, container role, visible button shape/slots, or system-surface markers).
5. Record the acceptance rule that no later Phase 26 slice may branch policy, telemetry, or resolution directly on raw `PageContextType` without first going through the mapper.

### Risks / Unknowns

- A single `PageContextType` may map differently depending on owner identity or button affordances, so the mapper must be allowed to use more than one field.
- Implementers may be tempted to let page context directly drive policy resolution because it feels simpler than formalizing the bridge.
- If the mapper is underspecified, timeline statistics and interruption telemetry may drift from policy resolution semantics.

### Done Criteria

- [ ] The Phase 26 planning package contains one explicit rule separating surface semantics from interruption semantics.
- [ ] The package contains one explicit one-way mapper rule from `PageContextType` to `InterruptionType`.
- [ ] Future slices no longer need to guess whether policy routing can branch directly on raw page-context categories.

- Existing interruption tools remain integration/reuse targets, not stubs to be replaced by a new page-context-specific resolver path.
